# Service Card: fictional worked example

From reader Chapter 5. Give consumers a usable task, access, configuration, support and unavailable-path contract. These are proposed or illustrative teaching records, not actual agreements or outcomes.

| Contract field | Proposed service behavior |
|---|---|
| Purpose | Draft an explanation of a bounded approved requirement for an authorized workflow |
| Required context | Validated caller, permitted workspace, task identifier, applicable evidence references, and agreed configuration |
| Prohibited authority | No eligibility decision, policy waiver, record write, or independent outreach |
| Evidence condition | Approved applicable source; missing/conflicting evidence follows a defined non-answer or review path |
| Configuration identity | Record the chosen model, instruction version, retrieval settings, evidence version, and relevant policy/evaluation versions |
| Result | Candidate explanation plus source references and a processing status defined by the interface contract |
| Operating limits | Agreed time, usage and cost limits; bounded retries; explicit unavailable behavior |
| Escalation | Named receiving function and supported route, with capacity agreed before use |
| Support and change | Technical owner maintains the service; domain owner judges task meaning; promotion requires relevant checks |
